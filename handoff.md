# Handoff — Эскада (saypavnik-code/career)

**Дата:** 2026-08-13
**Последний применённый патч:** v28
**Ветка:** main
**Стек:** Next.js 15 (static export), TypeScript, CSS Modules, localStorage

Этот документ — точка входа для новой сессии/чата. Он не пересказывает
каждый патч построчно (для этого есть история коммитов и сами файлы
патчей — они были untracked-скриптами, применялись через Codespaces и не
хранятся в репозитории), а даёт: что сейчас есть, как оно устроено, и что
имеет смысл делать дальше.

## Что такое Эскада

Личная профессиональная память сотрудника: быстрый захват мыслей, их
превращение в идеи и результаты (wins), карьерные подсказки на основе
реальной шкалы компетенций отдела, отчёты для performance review и
promotion case. Никакого task-менеджмента, дедлайнов, спринтов, процентной
оценки компетенций или AI-анализа без явного нажатия кнопки — это
осознанные и постоянные ограничения продукта.

## Архитектура

```
app/career/
  CareerDashboard.tsx      — весь UI (client component), ~850 строк
  career.module.css        — дизайн-система "Август" (CSS Modules)
  career-core.mjs          — состояние, миграции localStorage, доменная логика
  career-data.ts           — компетенции, уровни (реэкспорт из competency-knowledge)
  competency-knowledge.mjs — закрытая база критериев шкалы (12 компетенций × 3 уровня)
  local-guidance.mjs       — локальный (без внешнего AI) guidance-движок
  ai-contract.mjs          — closed-world контракт запроса/ответа для guidance
docs/
  ESCADA_PRODUCT_SPEC_V7.md, ESCADA_PRODUCT_SPEC_V8.md — продуктовые спеки
  PRODUCT_CJM_AND_RECOMMENDATIONS.md — CJM пользователя
  PHASE7_QA_REPORT.md — финальный QA-отчёт по AI-First roadmap (Phase 1-7)
tests/
  escada-v8.test.mjs, escada-v10.test.mjs
```

Данные — только в `localStorage` браузера (ключ `escada:v5`, схема версии 5).
Нет бэкенда для базовой работы. Опциональный внешний AI через
`NEXT_PUBLIC_ESCADA_AI_ENDPOINT`; без него работает `local-guidance.mjs`.

## Модель данных (текущая, schema v5)

- **Note** `{ id, title, body, rawText, createdAt, updatedAt, convertedIdeaId }`
  — заголовок всегда первые 4 слова первой непустой строки (`deriveNoteTitle`).
- **Idea** `{ id, title, details, nextStep, status, competencyIds, levelSignal,
  levelReason, behaviorRefs, workItems, notes, evidenceNotes, createdAt,
  updatedAt }` — UI показывает только title/details ("Смысл")/status/карьерную
  подсказку; `nextStep`/`workItems` остались в схеме для legacy-совместимости,
  но без UI для их редактирования (внутренний канбан этапов убран в v15).
  Статусы: `concept | preparation | in_progress | outcomes` (активный канбан,
  4 колонки) + `won | archived` (терминальные, вне канбана).
- **Win** `{ id, title, impact, evidence, metrics, confirmedBy, sourceContext,
  competencyIds, behaviorRefs, levelSignal, sourceIdeaId, workSummary,
  noteSummary, date, reportReady, createdAt }` — `sourceContext` = перенос
  поля "Смысл" идеи при конвертации в win (добавлено v18, миграция
  дозаполняется в v19).
- **Report** `{ id, title, type, periodStart, periodEnd, winIds, ideaIds,
  content, createdAt }` — 4 типа: `weekly | monthly | performance | promotion`
  (+ legacy `one-to-one`, оставлен для совместимости, не в UI-гриде типов).
  Черновики — **обычный текст**, не Markdown (с v20): заголовки секций
  заглавными без `#`, пункты через `•`, `Метка: значение` вместо `**жирный**`.

## Ключевые принципы (не менять без явного запроса)

- **Схемные миграции только добавочные**: никогда не редактировать уже
  опубликованную миграцию; фиксы — в новой версии схемы.
- **Расширение словарей, а не поломка старых полей**: при смене статусов
  идей (v14) и переходе Capture→Note (v13) старые значения не удалялись из
  типов — писалась функция миграции (`migrateIdeaStatus`, `captureToNote`),
  чтобы не сломать существующие данные пользователей.
- **AI только по явной кнопке**: `local-guidance.mjs` — обязательный fallback
  без сети; `ai-contract.mjs` — closed-world (только текущий и следующий
  уровень шкалы, никогда не выдумывает уровень выше "Ведущего специалиста").
- **CSS-токены только из `career.module.css`**: никаких хардкод-цветов в новом
  коде, только `var(--accent)`, `var(--lime)`, `var(--soft)` и т.д.

## Процесс работы (важно для новой сессии)

Каждая правка — отдельный Python-скрипт (`escada_<описание>_v<N>.py`),
который:
1. Верифицирует репозиторий (git fetch/status/HEAD == origin/main, чистое
   дерево — untracked-патч-скрипты игнорируются проверкой с v16).
2. Делает точечные `str.replace`-правки кода с явной проверкой "ровно один
   раз найдено, иначе fail" — никаких слепых перезаписей файлов.
3. Прогоняет `npm ci && npm run test:escada && npm run build`.
4. Коммитит и пушит в `main` **только** при полном успехе.

Каждый скрипт — новое имя файла, старые не переиспользуются
(`.gitignore` их не отслеживает). Работа всегда только в ветке `main`.

**Важно:** прежде чем писать новый патч, всегда собирается точная копия
текущего `main` (применением всех предыдущих патчей по порядку на чистый
чекаут) и на ней реально прогоняются `npm install`/`tsc`/`node --test`/
`next build` — не полагаться на то, что предыдущий патч-скрипт "должен был"
сработать корректно, а перепроверять фактическое состояние кода.

- **v18** (Phase 6) — подтверждение Win!, перенос «Смысл»→«Исходный контекст»,

- **v19** (Phase 7, финал roadmap) — QA-проход по всем 8 сценариям и 15

- **v20** — редизайн редактора заметки (был неоформленным textarea),

- **v22/v23** — последующие минорные funnel/UI-правки фактического main,
  включая сигнал «Готова стать win» непосредственно в канбане.
- **v24** — responsive/neo-glass polish без смены August design system;
  защита Note→Idea от дублей, видимая связь Idea→Win, повторное открытие

## Открытые вопросы (ничего не решено в одиночку)

- **DoD-пункт 7 из roadmap** ("идея = только название/смысл/статус/
  подсказка") сформулирован короче, чем секция 6.2 того же документа,
  против которой реально строилась карточка идеи (та явно оставляет
  компетенции, AI-панель и второстепенные секции). Ничего не удалялось на
  основании более сжатой формулировки — см. `docs/PHASE7_QA_REPORT.md`,
  раздел "Flagged".
- Report type `one-to-one` существует в данных и типах, но не показан в
  сетке выбора типа отчёта на экране «Отчёты» (там только 4 текущих типа).
  Не удалялся, чтобы не терять уже сохранённые отчёты этого типа у
  пользователей — но с этим ничего специально не делалось с v12.

## Как продолжить работу

1. Прочитать этот файл.
2. Если нужен контекст по конкретному прошлому решению — смотреть commit
   history в `main` (каждый коммит от патч-скрипта содержит подробное
   объяснение "почему", не только "что").
3. Новый патч — новый Python-скрипт с новым именем
   (`escada_<описание>_v22.py`), тот же процесс верификации/применения/
   тестов/коммита, что был у всех предыдущих.
