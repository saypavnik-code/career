# Эскада — продуктовый разбор и roadmap

**Цель продукта:** прозрачный инструмент роста сотрудника — документировать успехи, видеть ожидания по шкале, и в конце цикла иметь готовое к демонстрации доказательство роста. Главный риск — не функциональность, а *использование*: будут ли люди возвращаться в приложение сами, без напоминаний сверху.

Продуктовый разбор (что сделано хорошо, ключевые разрывы, принципы упрощения) — см. `docs/PRODUCT_CJM_AND_RECOMMENDATIONS.md`. Этот файл — только roadmap: что применено, что в работе, что дальше.

**О статусе этого документа:** файл переписывается целиком на каждом крупном шаге консолидации (после v38, теперь снова после v42), а не дополняется секциями — append-паттерн уже дважды приводил к рассинхрону с реальным `origin/main` в этом проекте. Актуальный baseline всегда проверяется через `git log --oneline -1 origin/main`, а не через этот файл.

---

## Два независимых трека работы

С v34 в проекте одновременно идут два трека, которые изначально были смешаны в одной нумерации:

1. **Архитектурный трек (Fable roadmap)** — патчи v34+, по итогам архитектурного ревью от Claude Fable (`fable-roadmap.md`). Устраняет структурные проблемы с доверием к данным (P0) и удобством (P1).
2. **Продуктовый фиче-трек** — v31–v33 (сделано до начала Fable-трека) плюс несколько пунктов, которые ещё не начаты (реальный AI-парсинг кастомной шкалы, свёртка шкалы-энциклопедии, ритм-напоминания).

Оба трека используют общую сквозную нумерацию патчей (`escada_patch_vN.py`) — это один и тот же протокол доставки, разные тематические группы работы.

### Отклонённые или сужённые пункты (проверены против фактического кода)
Каждый раз, когда план Fable roadmap проверялся напрямую против кода или внешней документации, находилось расхождение — план не принимается на веру без проверки:

- **Patch D, печать:** roadmap утверждал, что `window.open(..., 'noopener')` возвращает `null` и печать "никогда не работала". Проверено по актуальной MDN-спецификации `Window.open()`: `noopener` обнуляет `window.opener` внутри нового окна, а не возврат самого `open()`. Существующий код уже корректно проверяет `if (!printWindow)` на реальный случай отказа (блокировщик попапов). Изменение не внесено.
- **Patch E, объём:** roadmap просил полный id-based `useMemo`-рефакторинг редакторов idea/win/note. Проверка реальной раскладки UI показала, что конкретный сценарий (drag-and-drop мутирует idea, пока её же редактор открыт) физически недостижим — модалка редактора визуально закрывает список под собой. Патч v40 сужен до двух реально достижимых багов.
- **Patch F, реальность хуже плана:** при проверке старого SW-reload гейта обнаружился баг серьёзнее описанного в roadmap — проверка не включала `openNote`, то есть обновление сервис-воркера могло тихо перезагрузить страницу, пока открыта заметка с несохранённым текстом, без единого предупреждения.
- **Patch G, объём:** v42 закрыл только P1-1 (валидация ответа). P1-2 (payload budget для growth guidance) отложен в отдельный патч — см. "Дальше по очереди" ниже, там же измерения по фактическому размеру payload.

## Дальше по очереди

### Архитектурный трек (Fable roadmap) — приоритет
Полный список с инвариантами/тестами — в `fable-roadmap.md`. Кратко, в порядке зависимостей:

- **Patch G, остаток (P1-2):** payload budget для growth guidance. Сейчас `GrowthView` отправляет весь сырой массив `state.wins` без фильтрации. Измерено напрямую: один реалистичный объект `Win` сериализуется в ~938 символов; при заявленном лимите сервера ~24000 символов превышение наступает уже примерно на **26 wins** — вполне достижимое количество после 1–2 лет активного использования, то есть ровно тот сценарий использования, на который рассчитан продукт. Нужны агрегированные сигналы (счётчики по подтверждённым компетенциям, последние N win title+impact), а не сырой дамп — это отдельная по форме задача от валидационной работы v42, не быстрое продолжение.
- **Patch H** — migration normalization + error boundary (P1-4). *Подтверждено при работе над v38:* `migrateState` для `reports` делает только `Array.isArray(raw.reports) ? raw.reports : []` — нет `normalizeReport`, в отличие от `normalizeIdea`/`normalizeWin`. Это реальный пробел, не гипотеза.
- **Patch I** — multi-tab safety (P1-7)
- **Patch J** — contract cleanup: enums, types, унификация inference (P1-9)
- **Patch K** — scoped AI state per view (P1-10)
- **Открытое продуктовое решение (P1-8):** определение Idea → Work — нужно решить до патча, который трогает эту область

Следующий номер патча: **v44** (ориентировочно Patch H, либо отложенная половина Patch G — оба варианта разумны; подтвердить номер через `git log origin/main` перед стартом, как того требует протокол).

### Продуктовый фиче-трек — после архитектурного
- **Реальный AI-парсинг кастомной шкалы** — заменить `parseCustomScaleMock` в `custom-scale.mjs` на настоящий вызов модели (сигнатура уже совместима). Прокинуть `customScale` в тело запроса на `ESCADA_AI_ENDPOINT` (контракт готов с v32). Подобрать `competencyKeywords` для кастомной шкалы через модель, а не через частотный разбор текста. *Статус: всё ещё не сделано на v42* — заявлено как приоритет ещё до начала Fable-трека, так и не реализовано.
- **«Шкала» как ответ, а не энциклопедия** — свернуть список критериев (149 у дефолтной шкалы) за раскрывающийся блок по умолчанию; на видном месте — только текущий/следующий уровень и неподтверждённое; простой поиск/фильтр.
- **Мягкий ритм возврата** — локальное напоминание (PWA push, без сервера) раз в 1–2 недели без новых записей, тон спокойный; индикатор в интерфейсе (не push) — сколько дней с последней записи.

### Идеи на будущее (не приоритет сейчас)
- **Видимость для руководителя** — сейчас принципиально single-player (localStorage, один браузер). Нужен бэкенд — отдельный вопрос архитектуры вне текущего клиентского стека.
- Более лёгкий способ добавить Win прямо из идеи одним касанием («Готова стать win» частично уже есть).
- Сравнение «было полгода назад / сейчас» как отдельный визуальный артефакт для отчёта.

## Как понять, что упрощение работает

Три метрики, которые стоит отслеживать (даже простой localStorage-аналитикой, без бэкенда):
1. **Медианный интервал между записями** — снизится ли после ритм-напоминаний (пока не реализовано)?
2. **Доля циклов, где отчёт реально скопирован/экспортирован/сохранён** — должна расти после v27 и v38 (доступность истории отчётов).
3. **Доля идей/wins, привязанных к выбранному фокусу** — покажет, используется ли фокус (v33) на практике.
