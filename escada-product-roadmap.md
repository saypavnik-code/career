# Эскада — продуктовый разбор и roadmap

**Цель продукта:** прозрачный инструмент роста сотрудника — документировать успехи, видеть ожидания по шкале, и в конце цикла иметь готовое к демонстрации доказательство роста. Главный риск — не функциональность, а *использование*: будут ли люди возвращаться в приложение сами, без напоминаний сверху.

Продуктовый разбор (что сделано хорошо, ключевые разрывы, принципы упрощения) — см. `docs/PRODUCT_CJM_AND_RECOMMENDATIONS.md`. Этот файл — только roadmap: что применено, что в работе, что дальше.

**О статусе этого документа:** файл был переписан целиком при консолидации после v38, а не дополнен очередной секцией — предыдущая версия описывала baseline `f65cfd6` (после v28), когда реальный `origin/main` уже был на `20977ed` (после v33), что и создало путаницу в начале одной из прошлых сессий. Актуальный baseline всегда проверяется через `git log --oneline -1 origin/main`, а не через этот файл.

## Два независимых трека работы

С v34 в проекте одновременно идут два трека, которые *до этого файла* были смешаны в одной нумерации:

1. **Архитектурный трек (Fable roadmap)** — патчи v34–v38+, по итогам архитектурного ревью от Claude Fable (`fable-roadmap.md`). Устраняет структурные проблемы с доверием к данным (P0) и удобством (P1).
2. **Продуктовый фиче-трек** — v31–v33 (сделано до начала Fable-трека) плюс несколько пунктов, которые ещё не начаты (реальный AI-парсинг кастомной шкалы, свёртка шкалы-энциклопедии, ритм-напоминания).

Оба трека используют общую сквозную нумерацию патчей (`escada_patch_vN.py`) — это один и тот же протокол доставки, разные тематические группы работы.

### Отклонённый пункт (проверен и не подтвердился)
Fable roadmap для Patch D утверждал, что `window.open(..., 'noopener')` возвращает `null` и печать "никогда не работала". Проверено по актуальной MDN-спецификации `Window.open()`: `noopener` обнуляет `window.opener` внутри нового окна, а не возврат самого `open()`. Существующий код уже корректно проверяет `if (!printWindow)` на реальный случай отказа (блокировщик попапов). Печать, по всей видимости, работала верно всё это время — изменение не вносилось.

## Дальше по очереди

### Архитектурный трек (Fable roadmap) — приоритет
Полный список с инвариантами/тестами — в `fable-roadmap.md`. Кратко, в порядке зависимостей:

- **Patch E** — editor identity: id вместо snapshot (P1-5, частично P1-6)
- **Patch F** — unsaved-work guard + PWA reload safety (P1-6)
- **Patch G** — AI response validation + payload budget (P1-1, P1-2). *Важно:* `parseAndValidateAiResponse` уже существует в `ai-contract.mjs` — перед началом патча свериться, что именно он уже покрывает, а не считать это чистым полем
- **Patch H** — migration normalization + error boundary (P1-4). *Подтверждено при работе над v38:* `migrateState` для `reports` делает только `Array.isArray(raw.reports) ? raw.reports : []` — нет `normalizeReport`, в отличие от `normalizeIdea`/`normalizeWin`. Это реальный пробел, не гипотеза
- **Patch I** — multi-tab safety (P1-7)
- **Patch J** — contract cleanup: enums, types, унификация inference (P1-9)
- **Patch K** — scoped AI state per view (P1-10)
- **Открытое продуктовое решение (P1-8):** определение Idea → Work — нужно решить до патча, который трогает эту область

Следующий номер патча: **v39** (ориентировочно Patch E — подтвердить номер через `git log origin/main` перед стартом, как того требует протокол).

### Продуктовый фиче-трек — после архитектурного
- **Реальный AI-парсинг кастомной шкалы** — заменить `parseCustomScaleMock` в `custom-scale.mjs` на настоящий вызов модели (сигнатура уже совместима). Прокинуть `customScale` в тело запроса на `ESCADA_AI_ENDPOINT` (контракт готов с v32). Подобрать `competencyKeywords` для кастомной шкалы через модель, а не через частотный разбор текста. *Статус: всё ещё не сделано на v38* — это было заявлено как приоритет ещё до начала Fable-трека, но так и не реализовано.
- **«Шкала» как ответ, а не энциклопедия** — свернуть список критериев (149 у дефолтной шкалы) за раскрывающийся блок по умолчанию; на видном месте — только текущий/следующий уровень и неподтверждённое; простой поиск/фильтр.
- **Мягкий ритм возврата** — локальное напоминание (PWA push, без сервера) раз в 1–2 недели без новых записей, тон спокойный; индикатор в интерфейсе (не push) — сколько дней с последней записи.

### Идеи на будущее (не приоритет сейчас)
- **Видимость для руководителя** — сейчас принципиально single-player (localStorage, один браузер). Нужен бэкенд — отдельный вопрос архитектуры вне текущего клиентского стека.
- Более лёгкий способ добавить Win прямо из идеи одним касанием («Готова стать win» частично уже есть).
- Сравнение «было полгода назад / сейчас» как отдельный визуальный артефакт для отчёта.

## Как понять, что упрощение работает

Три метрики, которые стоит отслеживать (даже простой localStorage-аналитикой, без бэкенда):
1. **Медианный интервал между записями** — снизится ли после ритм-напоминаний (пока не реализовано)?
2. **Доля циклов, где отчёт реально скопирован/экспортирован/сохранён** — должна расти после v27 и v38 (доступность истории отчётов).
3. **Доля идей/wins, привязанных к выбранному фокусу** — покажет, используется ли фокус (v33) на практике.
