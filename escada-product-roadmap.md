# Эскада — продуктовый разбор и roadmap

**Цель продукта:** прозрачный инструмент роста сотрудника — документировать успехи, видеть ожидания по шкале, и в конце цикла иметь готовое к демонстрации доказательство роста. Главный риск — не функциональность, а *использование*: будут ли люди возвращаться в приложение сами, без напоминаний сверху.

Продуктовый разбор (что сделано хорошо, ключевые разрывы, принципы упрощения) — см. `docs/PRODUCT_CJM_AND_RECOMMENDATIONS.md`. Этот файл — только roadmap: что применено, что в работе, что дальше.

### В работе в этом спринте

v31, v32 и v33 поставляются в Codespaces **одним патч-скриптом** (`escada_patch_v32.py`), т.к. v32 технически зависит от кода v31, а v33 — от кода v32 (`activeCompetencies`); ни один из трёх ещё не был на `main`, когда разрабатывался следующий.

## Дальше по очереди

### v33 — Личный фокус на цикл ✅ разработано
*(ранее v29, разработан, но применение было пропущено — переразработан заново с учётом v31/v32)*
- Лёгкое поле «На чём я расту в этом цикле» — 1–3 компетенции, которые пользователь **сам** выбирает (не генерируются AI, AI может только подсказать через кнопку «Что развивать дальше?»).
- Идеи/Wins, созданные с нуля (не из карточки конкретной компетенции), по умолчанию наследуют `competencyIds` из фокуса.
- В «Рост» → «Мой путь» — «Не хватает по фокусу» и «Направления» сужаются до выбранных 1–3 компетенций вместо всех сразу; «Сильные сигналы» по-прежнему показывают весь реальный прогресс, даже вне фокуса.
- Работает одинаково для дефолтной и кастомной (v31) шкалы — `computeGrowthPath` принимает `focusCompetencyIds` третьим параметром и ищет их в том же массиве компетенций (`activeCompetencies`), что уже передаётся для v31/v32.
- Замена шкалы (v31) сбрасывает выбранный фокус — уже было заложено в `resetCycleForNewScale` при разработке v31.
- Если сохранённые id фокуса не находятся в активной шкале (например, шкалу заменили, а старый фокус остался) — интерфейс ведёт себя как без фокуса, а не показывает пустой экран.

### v34 — Реальный AI-парсинг кастомной шкалы
- Заменить `parseCustomScaleMock` в `custom-scale.mjs` на настоящий вызов модели (сигнатура функции уже совместима — см. `active-scale.mjs`/`ai-contract.mjs`, куда передаётся `activeScale`).
- Прокинуть `customScale` в тело запроса на `ESCADA_AI_ENDPOINT` — контракт уже готов с v32 (сервер пока может его игнорировать).
- Подобрать/сгенерировать `competencyKeywords` для кастомной шкалы через модель, а не через частотный разбор текста (сейчас — грубая эвристика в `active-scale.mjs`).

### v35 — «Шкала» как ответ, а не энциклопедия
*(ранее v29 в старой нумерации roadmap)*
- Свернуть полный список критериев (149 у дефолтной шкалы, произвольное число у кастомной) за раскрывающийся блок по умолчанию.
- На видном месте — только: текущий уровень, следующий уровень, и то, что ещё не подтверждено записями.
- Простой поиск/фильтр по компетенциям.

### v36 — Мягкий ритм возврата
*(ранее v30 в старой нумерации roadmap)*
- Локальное напоминание (PWA push, без сервера) раз в 1–2 недели без новых записей — тон спокойный, не геймификация.
- Индикатор в интерфейсе (не push) — сколько дней с последней записи, без осуждающего тона.

### v37 и далее — идеи на будущее (не приоритет сейчас)
- **Видимость для руководителя** — сейчас принципиально single-player (localStorage, один браузер). Если нужна видимость раньше финального отчёта — потребует бэкенда, это отдельный вопрос архитектуры вне текущего клиентского стека.
- Более лёгкий способ добавить Win прямо из идеи одним касанием («Готова стать win» частично уже есть).
- Сравнение «было полгода назад / сейчас» как отдельный визуальный артефакт для отчёта.

## Как понять, что упрощение работает

Три метрики, которые стоит отслеживать (даже простой localStorage-аналитикой, без бэкенда):
1. **Медианный интервал между записями** — снижается ли после v36 (ритм-напоминания)?
2. **Доля циклов, где отчёт реально скопирован/экспортирован** — уже должна расти после v27.
3. **Доля идей/wins, привязанных к выбранному фокусу** — покажет, используется ли фокус (v33) на практике.
